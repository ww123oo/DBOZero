# 翻譯與構建規則

本文檔是維護 `data/` 翻譯表和構建補丁時必須遵守的規則。
日常翻譯流程見根目錄 `README.md`，模組結構見 `docs/development.md`。

## 翻譯表規則

- TSV 檔案保持製表符分隔，不要用空格對齊欄。
- `data/new_translations.tsv`：日常新增詞條佇列，只填 `填写中文` 欄（表頭原文如此，請勿改名）；ID、原文、參考欄保持原樣。
- `data/translations.tsv`：已接受譯文主表，修改現有譯文時只改 `zh_cn` 欄。
- TBL 列的 `位置=*` 表示按原文做 UTF-16LE 通配替換，不要改成猜測的偏移。
- 候選／發現檔案（`reports/internal/`）不代表字串在遊戲裡可見。是否翻譯以使用者選擇、截圖或明確的文字相關性為準。
- `tbl0.pak` 的 `AzureRenegade`、`BurningRenegade` 是內部稱號特效權杖，必須逐位元組保持原文；`tbl1.pak` 裡帶空格的顯示名可以翻譯。

## 文字來源優先順序

- 短普通 UI 標籤、屬性名、狀態標籤等非富文字，預設以 `local_data.dat` / `local_sync_data.dat` 為準。
- 富文字、長文字、彈窗訊息、系統訊息，以及已知執行時期來源是 `lang0`/`tbl` 的新 UI/TBL 文字，用 `lang0.pak` 或 TBL。
- 不要讓舊的 `local_data.dat` 措辭覆蓋新元素術語。水／火／冰／雷／風等新屬性內容保持當前 `lang0`／新內容譯法，除非有執行時期證據表明用了別的來源。
- 如果某個可見短標籤確實來自 `lang0.pak`（即使 `local_data.dat` 裡也有同 key），先透過截圖或輸出位元組驗證執行時期來源，再加窄範圍的 `lang0` 特例。
- 已驗證的 `lang0.pak` 擁擠狀態標籤模式是定長單引號替換：把整個帶引號欄位（如 `"STR"`）替換為等長值（如 GBK 下的 `力量 `）。僅當輸出檔案大小不變且遊戲實測接受時才允許。
- 不要把單引號 `lang0` 模式當成通用策略；目前只限於已驗證的六個基礎狀態屬性等短標籤，新案例需單獨測試。

## 編碼與打包規則

- `local_data.dat`、`local_sync_data.dat` 產生為 ANSI 遊戲檔案，不是 UTF-8。
- 面向遊戲的產生檔案絕不能轉換成 UTF-8 中文文字。
- `lang0.pak` 使用固定原始位元組補丁，是唯一有原始欄位長度硬限制的面。譯文 GBK/CP950 轉換後超長就必須縮短。
- `lang0.pak` 的長度規則不適用於 Taiwan/RDF 或 TBL。
- TBL 字串是定長二進位欄位。儲存長度前綴保持不變；較短的 UTF-16LE 替換串用 NUL 位元組（`00 00`）補齊，絕不用可見空格（`20 00`）。
- 不要為了讓 TBL 名稱匹配舊文字長度而手動縮短，除非補丁器回報了真正不安全的列。

## 源快照刷新規則

`src_file/DBOZero` 被更新為新版遊戲快照時：

0. 前提：遊戲目錄必須是**官方原版檔案**。如果先打了補丁再刷新，`dboc refresh`/`update` 會偵測到遊戲檔案與構建輸出逐位元組一致並拒絕同步；此時用啟動器檔案校驗／修復恢復原版後再執行。安全順序：遊戲更新 → 先刷新／更新 → 再把補丁覆蓋進遊戲。
1. 執行 `dboc update`；它會自動建立本機 Git 恢復點，並包含已追蹤的 `data/new_translations.tsv` 變更。
2. 手動分步執行時，先建恢復點再 `dboc scan`。
3. 手動翻譯完成後執行 `dboc build`。
4. 檢查構建統計，重點是 `pack/lang0.pak`、`pack/tbl0.pak`、`pack/tbl1.pak` 的 `missing` 計數。
5. 如果固定 TBL 列發生移動，優先用當前 v3 資料；只有明確需要恢復舊 override 時才用 legacy 重定位腳本。
